 Composite keys:
  In the world of databases, a **composite key** is a primary key that consists of **two or more columns** (attributes) to uniquely identify a row in a table. 

While a standard primary key usually involves just one column (like an `Employee_ID`), a composite key is necessary when no single column can guarantee uniqueness on its own.

---

## How It Works
Think of it like a coordinate system. A single "Latitude" doesn't tell you exactly where you are on Earth—you need both "Latitude" and "Longitude" to pinpoint a specific location.

### Key Characteristics:
* **Uniqueness:** The combination of values in the composite columns must be unique for every row.
* **No Nulls:** Just like a standard primary key, none of the columns involved in a composite key can contain `NULL` values.
* **Minimalism:** You should only include the minimum number of columns necessary to achieve uniqueness.



---

## A Real-World Example
Imagine a database for a **University Enrollment** system. 

If we have a table called `Enrollments`, we might have the following columns:
1.  `Student_ID`
2.  `Course_Code`
3.  `Semester`

* A `Student_ID` isn't enough to be a primary key because a student can enroll in many courses.
* A `Course_Code` isn't enough because many students can take the same course.

However, the combination of **`Student_ID` + `Course_Code`** ensures that a specific student cannot be enrolled in the exact same class twice in the same record. Here, the two columns together form the **Composite Key**.

| Student_ID | Course_Code | Grade |
| :--- | :--- | :--- |
| 101 | CS50 | A |
| 101 | MATH10 | B |
| 102 | CS50 | A |
| **101** | **CS50** | **Error (Duplicate Key)** |

---

## When Should You Use One?
Composite keys are most frequently used in **junction tables** (also known as mapping or associative tables). These tables sit between two other tables to create a **Many-to-Many relationship**.

> **Note:** Many modern developers prefer using a **"Surrogate Key"** (an artificial, auto-incrementing ID like `id: 1, 2, 3...`) instead of a composite key because it keeps foreign key relationships simpler and indexed faster. However, composite keys are still mathematically "pure" and excellent for ensuring data integrity at the schema level.

So, CORS let us make requests from a web browser on one domain to server on a different domain.
